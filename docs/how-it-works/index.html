How the provably fair draw works

The whole algorithm, with the numbers of one real example round worked through.

1. The commitment: a hashed server seed

The server picks a random 32-byte server seed and shows you only its SHA-256 hash. The hash reveals nothing about the seed, but it pins it: no other seed has the same hash.

server seed      0f1e2d3c4b5a69788796a5b4c3d2e1f00112233445566778899aabbccddeeff0
SHA-256 (shown)  afa880ca0c7da502fc32ab284cf70852ef7c5540204e4215c2a1617074ca7905

2. The byte stream: HMAC-SHA256

Each round is keyed by the raw server seed and the message clientSeed:nonce:round. The nonce counts your rounds on this seed pair; round counts 32-byte blocks when a game needs more than 32 bytes.

key      = server seed (32 raw bytes)
message  = "gift-club-demo:0:0"        // clientSeed:nonce:round
block    = HMAC-SHA256(key, message)
bytes    = 1a bc a7 1f 1b 42 64 c5 …

3. From bytes to numbers

Every four bytes make one float in [0, 1). The formula is exact, so the verifier compares the underlying 32-bit integer, never a rounded decimal.

float = b0/256 + b1/256² + b2/256³ + b3/256⁴
      = 26/256 + 188/65536 + 167/16777216 + 31/4294967296
      = 0.1044411135

4. From numbers to a result

Each game turns its floats into an outcome by its own published rule: a row of left/right bounces in Plinko, a shuffled deck in Blackjack, a ticket number in a box. The game modules in src/games/ hold each rule and each pay table.

5. Payout rounding

A win in Stars is a whole number. When bet × multiplier has a fraction, one more float decides whether it rounds up, so the rounding is provably fair too. Gram payouts are floored to the nanoton instead and draw no rounding float.

Pay table versions

When a pay table is retuned, the old one stays in the code under its version number. A round is always checked against the version it was played on, which the round's details show.

Run the tests yourself

The test suite replays thousands of rounds the server computed and checks every byte:

git clone https://github.com/gift-club/provably-fair-verifier.git
cd provably-fair-verifier && npm install && npm test

Questions

Why HMAC-SHA256 and not a plain random number?

Because it is deterministic: the same seeds and nonce always give the same bytes, so a result can be re-computed and checked. A plain random number cannot be checked after the fact.

Can the same seeds produce two results?

No. Every round uses a new nonce, so no two rounds on one seed pair share their bytes.

Where are the game rules?

In src/games/, one file per game, each with the pay tables the server uses.
